# 單卡執行流程

本流程整理自[C11-NWT實際交付](../work/C11-NWT/2026-11-17-02/REPORT.md)，搭配[工作項目](WORK_ORDERS.md)、[交付契約](DELIVERY_SPEC.md)、[來源路線](SOURCE_MAP.md)及[接入規範](../ADDING_DATA.md)使用。規定流程與實際驗收結果分開；既有卡的通過結果不能代替新批次驗證。

## 任務範圍

使用者指定「執行＋完整卡號」時，預設包含該卡完整查找、原件保存、候選整理、驗證、可新增資料匯入本機平台及交付報告，不再另問是否匯入。使用者明說只抓取、只要工作包、只做設計或禁止匯入時，依該次限制執行。不能因0筆可新增就略過重新查核；既有不同內容只能交更新提案。

每次只完成指定卡；超過6份來源文件／6個情境或3組針對性搜尋的部分列精確缺口與續卡。辦理資訊保留卡若尚無情境及DoD，先補齊範圍再執行。不得替使用者標✅、覆寫舊資料、直接編輯SQLite、修改before_p或公開部署。

## 1. 建立本次基準

- 讀當次適用AGENTS、README、卡片及A1–A6／N1–N9；逐項對應交付及驗證。
- 用實際執行日期建立新的`work/<完整卡號>/<YYYY-MM-DD>-<run>/`，不沿用或改寫先前工作包。程式、來源日期、舊候選與數字都要重新確認。
- 以SQLite `mode=ro`讀取categories、records、reviews、events、imports、meta。保存可逐筆比較的基準或摘要及完整比較依據；不能只比總筆數。before_p只讀相關記錄，保存穩定ID映射。
- 依地區、方案、服務、年齡、序位／身分、金額性質、期間辨識相同情境。已有分類完整複製SQLite設定，已有情境沿用ID，不按日期創造替代ID。
- 盤點時不GET正式資料API，因為GET會掃描imports，可能寫庫。正式匯入前才確認服務及待匯入檔；預先存在的錯誤或非本次批次不能擅改。

## 2. 取得來源與對照原文

- 從來源路線追主管機關現行正文、附表或機構具名價目；入口、搜尋摘要與舊快照只能協助定位。
- 相同網域至少間隔2秒，原件下載25秒逾時且不自動重試；遇登入、驗證碼、403停止該路徑，不對外聯繫。逾時記錄失敗，改找獨立官方來源，不能把失敗當無制度。
- 保存原件及metadata：source ID、標題、原URL、final URL、取得時間、HTTP結果、SHA256。衍生txt保留頁碼，不取代HTML／PDF原件；OCR數字與註腳必須對照影像。
- 對照金額、單位、定額／上限／加發／自付等性質、提供者、地區、適用期間、資格及限制。公布日、修正日、出生適用起日、下載日分開，未知為null。
- 官方資料不一致時保留兩邊定位，逐欄標conflict及影響；若差異影響該情境金額或適用性，不匯入未決情境。非核心特殊情境差異可附明確排除／未決說明交付，不將整套資格說成通過。

## 3. 產生完整候選及新增包

依DELIVERY_SPEC交REPORT、candidate、EVIDENCE、MAPPING、CHANGES、SNAPSHOTS與raw。只在有可新增資料時產生import-ready；完整候選與新增包用不同batch_id，按分類分檔。

| 平台比對 | 處理 |
| --- | --- |
| 無此情境且證據支持 | 完整candidate＋import-ready |
| 已有且一致 | 完整candidate＋本次證據，不新增、不改review |
| 已有但內容不同 | 沿用ID，完整candidate＋CHANGES更新提案，不放新增包 |
| 核心來源未決 | 明列缺口、影響及下一步，不用舊值／猜值湊新增 |

一致／需更新須逐欄比對實質資料；僅checked_at、下載時間或新快照不同時，本次證據保存work，不藉新增匯入更新既有來源或日期，也不因此判定金額改變。

來源locator保留條次、表列、頁碼與註腳即可；完整雜湊放證據側檔及metadata。C11-NWT曾因畫面locator顯示64字元雜湊而在手機溢出，移至側檔後通過。每批仍需實測來源展開狀態，不能因舊批次正常就略過。

## 4. 匯入前驗證

1. 只呼叫`importing.validate_batch`驗證candidate與import-ready；此階段不建立正式Store、不掃正式imports。重算原件SHA256，逐筆檢查來源、數字、單位、地區、期間、null、公式、衝突與情境涵蓋。
2. 深度比對新增包與完整候選中的對應record，確認既有ID、語意情境及分類設定無衝突。
3. 按README執行必要檢查；先讀腳本確認使用暫存資料庫。現行共用檢查如下，各指令失敗立即處理，不以後續成功掩蓋前一失敗：

```sh
uv run --project data_validation python -m unittest discover -s data_validation/tests -v
node --check data_validation/web/app.js
node data_validation/tests/browser.mjs
node data_validation/tests/import-browser.mjs
node data_validation/tests/sidebar-browser.mjs
```

4. 對本批資料建立暫存DB驗收：用SQLite backup API從只讀正式連線複製一致快照，僅在暫存目錄放本批新增檔、啟動獨立測試port。驗證分類、筆數、重要欄、初始狀態、來源及背景、390／1440px（含來源展開）、整頁保存、全部正確含隱藏欄、修正保存與套用分離、轉正確、重載、歷史及重複匯入；逐筆比較既有records／reviews／events未變。
5. 可參考C11-NWT工作包中的verify.mjs，但不可直接套用其卡號、固定筆數、金額、review狀態或port。重跑已有分類時驗證review保留，不要求已核對欄回到pending；純抓取或無新增情境時，REPORT標明哪些入庫驗收不適用及原因。

暫存驗證可呼叫保存／套用；正式平台僅執行授權新增及讀取，不能把測試修正值寫入正式資料。檢查port歸屬，不能把測試指向使用者服務或終止不屬本任務的程序。檢查通過後不擴張無關測試。

## 5. 新增入庫與正式確認

- 匯入前再次以只讀方式比對正式基準；若期間有使用者變更，重新計算分類／語意去重及新增包，不覆寫變更，也不把它誤判為本次破壞。
- 確認本機服務指向目標data目錄；服務未啟動可按README啟動本機服務。禁止為本任務刪庫重建或清除舊imports。
- 新增包以新檔名先寫`.tmp`、寫完原子改名`.json`放data/imports，保留work內交付副本。candidate不直接放imports，成功批次不得再修改。
- GET資料API觸發匯入；確認import_results、實際新增筆數、category及records與候選逐筆一致。再次GET確認筆數、revision、歷史不重複增加。
- 深度比較舊records、reviews及歷史原列保留；只新增預期分類／記錄與import事件。新記錄重要欄初始pending，不新增假核准review。有失敗先回報原因，不改舊資料強行通過。
- 正式瀏覽器只讀檢查新／既有分類直接網址、重載、來源、數字與兩個尺寸，保存截圖及IMPORT_RESULT.json；不點保存、套用或全部正確。

## 6. 交付與DoD

REPORT逐項記A1–A6、適用N1–N9的通過／未通過／未驗證／不適用（附理由），連到實際測試輸出、原件、截圖及匯入結果。保留失敗、修正及重驗結果，不用驗收清單代替執行證據。必要條件未過就標部分完成；未知或衝突精確到欄位及情境。

交付含指定情境、完整候選、新增、一致、需更新、來源未決數量，以及網址、缺口與未做範圍。更新README的實際涵蓋與報告連結；重跑未新增時不能虛增筆數或宣稱新增頁。最終回覆簡述結果、實際驗證、分頁／報告與未解限制。

## 本流程文件的DoD

| 編號 | 驗收條件 | 驗證方式 |
| --- | --- | --- |
| P1 | 工作清單每列為完整唯一卡號，原情境、來源、分類、ID規則可追溯 | 新舊卡號及逐列範圍核對；詳細規格連結檢查 |
| P2 | 指定卡號的預設範圍、只抓取例外及授權界線一致 | WORK_ORDERS、DELIVERY_SPEC、COLLECTION_PLAN、README及本流程交叉檢查 |
| P3 | 流程可重現原件保存、完整候選／去重、暫存驗證、原子匯入與正式保留檢查 | 每階段有輸入、操作與可檢查結果，對照C11-NWT實際報告 |
| P4 | 不把舊結果當新批次驗收，不遺漏失敗／衝突／空值／不適用項 | 本流程與A1–A6／N1–N9逐項核對 |
| P5 | 文件連結及範本符合目前檔案／validator，文件修改不動正式資料或程式 | 相對路徑、JSON範本與檔案內容核對；結果記於DESIGN_VERIFICATION |

上述P1–P5只判定本次文件交付；未執行任何其他卡片的資料抓取或入庫。後續每卡仍須實際完成A1–A6及適用N1–N9。

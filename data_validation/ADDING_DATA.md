# 新增資料與分類接入規範

已實作：將批次JSON放入 `data/imports/`，重新整理網頁便會自動匯入，新分類出現在左側，既有分類的新資料進入原分頁。無須重啟服務或修改程式。

## 使用步驟

1. 複製 [examples/new-category.json](examples/new-category.json) 到工作用檔案，替換示範分類、資料與真實來源。範例不是政策資料，尚未放入自動匯入目錄。
2. 設定新的batch_id與穩定的record id；category.id決定網址（例如example-service對應 `/example-service`）。category.order控制左側順序，同序依id排序。
3. 編輯完成後將檔案放到 `data/imports/<batch-id>.json`。只掃描這一層的.json；可先寫.tmp，完成後改名.json，避免編輯一半被讀取。
4. 重新整理平台任一頁面。平台驗證整批後自動寫入SQLite，無額外確認步驟。新分類自動出現；新資料預設⏳，沿用所有核對／儲存／套用／歷史功能。
5. 不合法的檔案顯示檔名與原因，整檔不寫入；修改未匯入檔案再重新整理。其他合法檔案仍可匯入。已匯入檔案不再修改，新增資料另開新批次。

每次讀取資料API、開啟分類網址及送出儲存／套用前掃描。沒有背景輪詢，不會主動刷新而清掉草稿；送出前若匯入造成版本改變，回409並保留草稿。

SQLite是唯一主資料。`data/records.json`仍僅作首次初始化，不是新增資料入口。刪除匯入檔案不會刪除已匯入的分類、資料或歷史。匯入JSON原文與雜湊保存於SQLite的imports表，不依賴外部檔案持續存在。

新增相同批次應無變更；相同ID但不同內容應列衝突並拒絕覆寫。現有內容的修正走核對／套用流程。來源更新若要批次取代既有內容，須另設有差異預覽的更新流程，不能沿用新增匯入偷偷覆寫人工修正。

## 資料契約

批次檔放 `data/imports/<batch-id>.json`，單檔最多5MB／1000筆。下例只有結構示意；records為空可建立空分類，所有操作按鈕停用。完整有資料範例見examples/new-category.json：

```json
{
  "schema_version": 1,
  "batch_id": "example-20261114-001",
  "category": {
    "id": "example",
    "title": "新資料類型",
    "description": "本頁涵蓋的地區、期間與尚未收錄範圍",
    "order": 30,
    "review_fields": ["金額", "條件", "限制"],
    "field_types": {"金額": "integer", "條件": "text", "限制": "text"}
  },
  "records": []
}
```

每筆record沿用現有欄位結構：

| 欄位 | 規則 |
| --- | --- |
| `id` | 全平台唯一且穩定；不得含 `::`，現有review key使用此分隔符 |
| `type` | 必須對應分類id；slug只允許小寫英數及連字號，不與api或靜態檔案網址衝突 |
| `title` | 可讀的具體情境，包含必要的方案／子女序位等區別 |
| `fields` | 欄名對應文字或null；金額依現有格式用數字字串，另存單位；未知不寫0 |
| `sources` | 至少一個來源，每個含title、可定位的http(s) url及locator；不能用搜尋摘要當金額依據 |
| `checked_at` | 真正來源核對日期，未核對用null，不把匯入日當核對日 |
| `provenance` | 資料來源、核對程度與待查缺口，不宣稱全部資格已確認 |

金額資料須有提供者、地區、單位、適用期間、條件及來源；背景欄位放fields，未知保留null。中央與地方資料分清楚。既有record ID及來源參照不可因匯入改名。

只挑影響使用者判斷的重要欄位核對，預設金額／條件／限制。新類型不適用這三欄時，在分類設定明確列出少量必要欄位，不硬塞金額、不把所有背景欄位變成核對項。新增欄位不自動加入review_fields。review_fields限1至5個不重複欄名，每筆必須具備，可填null。field_types指定text（非空文字）、integer（非負整數文字）或date（YYYY-MM-DD有效日期），前後端共用設定。未指定時金額預設integer，其餘text。文字最多10000字。匯入檢查格式及來源網址結構，不自動確認政策真假或連結可用性。

## 共用接入機制

- 分類建立SQLite `categories` 表作為唯一分類登錄，API回傳有序清單及各類重要欄位。批次檔是輸入快照，不能與資料庫同時成為兩份主設定。
- 遷移時建立既有allowance／childcare分類，保留既有網址、ID、資料、reviews與events；不得重新匯入快照覆蓋現有資料。
- 前端由分類清單建立左側直列選單、頁面標題與範圍。空分類顯示無資料且停用操作；未知分類顯示找不到分類，不默默轉到津貼頁。
- 後端路由與儲存／套用驗證使用同一分類登錄；重要欄位從該類設定取得，不能只改前端。
- 共用⏳／✅／❌、至少44px點擊區、全部正確、整頁儲存、篩選、草稿離頁提示、來源、套用與歷史。全部正確包含本頁隱藏欄位，但不跨分類。
- 套用只更新本頁已儲存的錯誤修正；成功後改✅並收起輸入，保留錯誤判斷及修改前後值。
- 匯入事件保存批次ID、內容雜湊、時間、操作者、新增分類與記錄內容。新增原值為null，after為完整記錄。批次JSON原文保留以便定位（不自動下載來源網頁）；相同批次不同雜湊拒絕。
- 匯入、儲存及套用均採交易與版本檢查。新資料加入後提升revision，舊頁送出時拒絕覆寫；失敗整批回滾。
- 新增事件種類時同步調整修改紀錄呈現，不假設所有事件都有review的status或key。

| 編號 | 必要驗收案例 | 驗證方式 |
| --- | --- | --- |

| N5 | 修正儲存未套用前主資料不變；套用後主資料改變、狀態✅，歷史有前後值 | API＋瀏覽器＋重啟 |
| N6 | 重複匯入不新增；不同內容同ID／同batch衝突、無效來源、分類或欄位整批拒絕 | 暫存DB測試 |

| N8 | 新分類390／1440px正常，長分類名、空分類、未知路徑、讀寫失敗可處理 | 瀏覽器驗證 |

範圍不含公開發布、before_p同步、補齊未指定政策或新增登入系統。


## 既有分類加資料與衝突處理

既有分類新增資料時，沿用category設定，records只放新ID，另給新batch_id。可從瀏覽器開啟 `/api/data` 的categories複製目前設定，或沿用該分類先前批次的category。既有分類的title、description、order、review_fields、field_types如不同則整批拒絕，不藉匯入修改分類設定。

- 同batch_id／相同JSON內容：不新增、不提升版本。JSON鍵順序及空白差異不影響比對。
- 同batch_id／不同內容：拒絕，還原已匯入原檔，新資料使用新batch_id。
- 新batch_id／相同record id與相同目前內容：略過該筆；仍保存新批次及匯入事件。
- 新batch_id／相同record id但內容不同：整批拒絕，包含已有人工修正的情況。
- 新增欄位或變更既有資料不屬新增匯入，須另做有差異審查的更新流程；目前未提供此功能。可核對欄位的修正仍透過頁面套用。

檔案頂層只接受schema_version、batch_id、category、records。record只接受表列七欄，避免拼錯欄位卻靜默忽略。來源只接受title、url、locator；網址限http(s)，不可含登入資訊。分類id最多64字，以小寫字母開頭，後續允許小寫英數與連字號；api、app、style、index為保留名稱。
